# 金铲铲之战自然之力智能推荐系统双人分工计划

## 1 项目信息

- 项目名称：金铲铲之战 S18 自然之力实时视觉分析与智能推荐系统
- 项目人数：2 人
- 当前阶段：已完成立项，进入需求分析与总体设计阶段
- 基准赛季：S18 自然之力
- 基准版本：18.4
- 计划周期：2026 年 10 月 19 日至 2026 年 12 月 27 日，另设一周缓冲

成员姓名确定后，将文档中的“成员 A”和“成员 B”替换为真实姓名。

## 2 分工原则

两名成员分别负责一条可以独立推进的技术主线，同时通过统一的数据格式和接口完成集成。

- 成员 A 主线：游戏数据、推荐算法、后端服务和算法实验。
- 成员 B 主线：实时画面采集、视觉识别、前端界面和演示体验。
- 共同任务：需求确认、系统设计、接口联调、综合测试、报告、PPT 和现场答辩。

成员 A 不需要等待前端完成即可通过接口测试推荐算法；成员 B 不需要等待推荐算法完成即可使用模拟数据开发界面。双方从第二周开始约定接口，减少后期集成风险。

## 3 成员职责

### 3.1 成员 A 数据算法与后端负责人

主要职责：

1. 采集并整理自然之力 18.4 的英雄、装备、羁绊和阵容数据。
2. 建立数据字典、版本字段和 SQLite 数据库。
3. 实现装备合成、英雄查询、羁绊计算等基础逻辑。
4. 设计候选阵容生成、特征计算、加权评分和推荐解释算法。
5. 使用 FastAPI 提供数据查询、推荐和阵容分析接口。
6. 准备推荐算法测试案例，完成基线对比和权重实验。
7. 配合成员 B 完成识别结果到推荐接口的转换。
8. 负责报告中的数据设计、推荐算法、后端实现和实验分析章节。

核心交付物：

- 游戏数据集与数据来源记录
- 数据库与初始化脚本
- 推荐算法模块
- FastAPI 后端服务
- API 文档与接口测试
- 推荐算法实验结果

### 3.2 成员 B 视觉识别与前端负责人

主要职责：

1. 确定实时识别的游戏界面、分辨率和识别区域。
2. 使用 OpenCV 实现游戏窗口捕获、定时抽帧和区域裁剪。
3. 建立英雄和装备图标样本，完成模板匹配或 YOLO 识别原型。
4. 实现多帧结果确认、置信度过滤和人工纠错功能。
5. 使用 Vue 开发数据浏览、资源选择、阵容推荐和阵容分析页面。
6. 接入成员 A 提供的后端接口，展示推荐结果和分项评分。
7. 完成实时识别状态、暂停识别、错误提示和演示模式。
8. 负责报告中的视觉识别、前端设计、系统演示和用户体验章节。

核心交付物：

- 实时画面采集模块
- 英雄与装备识别样本
- 视觉识别模块及准确率统计
- Vue 前端页面
- 人工确认与纠错功能
- 演示截图和备用演示视频

### 3.3 共同职责

- 审核需求范围和技术路线。
- 绘制系统架构图、业务流程图和数据库 ER 图。
- 共同制定前后端接口和视觉识别输出格式。
- 每周进行代码合并、进度检查和风险调整。
- 完成功能测试、集成测试和课堂演示测试。
- 共同撰写项目总结、创新点、问题与展望。
- 共同制作汇报 PPT，并分别准备自己的答辩部分。

## 7 接口与交接标准

### 7.1 统一数据标识

英雄、装备、羁绊和阵容必须使用稳定 ID，禁止仅用中文名称作为唯一关联字段。所有数据至少包含：

- `season`：赛季标识，例如 `s18`
- `version`：版本标识，例如 `18.4`
- `id`：实体唯一标识
- `name`：中文显示名称
- `source_url`：数据来源
- `collected_at`：采集时间

### 7.2 视觉模块输出

成员 B 的识别模块输出统一 JSON：

```json
{
  "frame_time": "2026-11-30T20:30:00+08:00",
  "source": "game_window",
  "champions": [
    {"id": "champion_id", "name": "英雄名称", "confidence": 0.93}
  ],
  "items": [
    {"id": "item_id", "name": "装备名称", "confidence": 0.89}
  ]
}
```

低于置信度阈值的结果必须进入人工确认，不直接写入推荐输入。

### 7.3 推荐接口输出

成员 A 的推荐接口至少返回：

- 候选阵容 ID 和名称
- 综合评分及分项评分
- 已拥有英雄和缺失英雄
- 推荐装备分配
- 激活羁绊
- 推荐理由和阵容风险

### 7.4 交接完成条件

模块交接不能只发送代码，必须同时提供：

1. 启动方式与依赖说明。
2. 输入输出示例。
3. 正常案例和异常案例。
4. 已知问题与限制。
5. 对应的测试方法。

## 8 协作与代码管理

建议使用 Git 进行协作，主要分支如下：

- `main`：仅保存可运行、可演示的稳定版本。
- `develop`：日常集成分支。
- `feature/data-recommendation`：成员 A 的数据与推荐开发分支。
- `feature/backend-api`：成员 A 的后端接口分支。
- `feature/frontend`：成员 B 的前端开发分支。
- `feature/vision`：成员 B 的视觉识别分支。

协作规则：

1. 每个功能通过独立提交完成，提交信息说明修改模块和目的。
2. 不直接在 `main` 分支开发。
3. 合并前必须完成本模块基本测试。
4. 每周至少合并一次 `develop`，避免长期分支冲突。
5. 数据文件修改前先沟通，避免双方同时修改同一文件。
6. 密钥、账号、缓存、模型临时输出和大型视频不提交到仓库。

## 9 每周协作机制

### 9.1 周初计划

每周开始时用 15 至 20 分钟确认：

- 本周各自需要完成的任务。
- 双方存在的接口依赖。
- 本周可展示的最小成果。
- 可能延期的任务及替代方案。

### 9.2 周中联调

周中进行一次短联调，成员 A 提供可调用接口或模拟返回，成员 B 提供页面或识别输出，尽早发现字段不一致问题。

### 9.3 周末检查

每周结束时记录：

- 本周计划任务是否完成。
- 已提交的代码、文档或测试证据。
- 仍未解决的问题。
- 下周任务是否需要调整。

## 12 风险与替补方案

| 风险 | 主要负责人 | 应对措施 |
| --- | --- | --- |
| 数据无法自动采集 | A | 使用公开页面加人工校验，先建立小而完整的数据集 |
| 推荐效果不稳定 | A | 保留规则与固定权重基线，使用人工标注案例调参 |
| 实时识别准确率不足 | B | 限定分辨率和区域，改用模板匹配并增加人工确认 |
| YOLO 数据量不足 | B | 不强行训练模型，优先使用模板或特征相似度 |
| 前后端接口变化频繁 | A、B | 第二周确定接口，使用模拟数据并保留版本号 |
| 一方任务延期 | A、B | 先保证 P0 功能，另一方协助数据录入或测试 |
| 现场识别失败 | B | 准备固定截图、录屏和手动选择输入三种备选方案 |
| 现场后端无法启动 | A | 准备一键启动脚本、本地数据库和接口返回样例 |

## 13 双方验收标准

### 成员 A 完成标准

- 自然之力 18.4 数据可查询且包含版本信息。
- 推荐接口可以根据已有英雄和装备返回候选阵容。
- 推荐结果包含分项评分、缺失资源和至少两条解释。

- 识别结果显示置信度并允许人工修正。

- 有识别准确率统计、演示截图和备用视频。

- 系统形成“实时画面采集、视觉识别、人工确认、AI 推荐、阵容分析”的完整闭环。
- 核心流程可在本地环境稳定运行。
- 推荐计算目标响应时间不超过 3 秒。
- 项目报告、PPT、源代码和演示材料内容一致。
- 任一成员都能够独立完成基础启动和完整演示。
