# 第一周视觉方案选择

## 路线结论

优先采用“固定游戏客户区 → 商店卡位裁剪 → 图像预处理 → 模板匹配/特征相似度 → 多帧稳定 → 人工核对与购入确认”。当前为设计结论，尚未有真实截图、图标模板或识别实测结果。

| 方案 | 条件与成本 | 本项目决策 |
| --- | --- | --- |
| 固定区域模板匹配 | 固定尺寸、模板与卡牌美术一致时成本低，易解释 | 首先验证 |
| 颜色/局部特征相似度 | 可补充部分亮度、缩放差异；需要实测区分相近英雄 | 作为候选对比 |
| YOLO | 需要足够标注样本、训练及误差评估 | 模板方案证据不足后再评估 |
| OCR 商店文字 | 依赖字体、缩放、文本区域 | 首版不选，符合第一周范围 |

英雄详情图、游戏头像和商店卡牌可能存在美术版本或裁剪差异，不能直接把 A 数据中的英雄展示图视为匹配模板。后续以同分辨率商店图像建立对应稳定 ID 的模板，并记录来源。

## 采集技术选择

- 本地 Python 负责采集，Vue 浏览器页面负责控制状态和显示结果；浏览器不直接枚举 Windows 原生窗口。
- 首选评估 `mss` 捕获可见游戏客户区，Windows 原生窗口 API 提供选择与客户区尺寸信息，OpenCV 用于裁剪和识别。
- `mss` 可能截到遮挡窗口、黑屏或桌面；最小化/遮挡时不能宣称后台捕获可靠。后续用真实模拟器验证，必要时评估 Windows Graphics Capture 等替代方式。
- 本周不安装采集依赖，不请求管理员权限。Git 推送使用本机凭据管理器已有登录。

## 匹配与稳定规划

1. 以配置提取各卡位，统一模板和候选图像大小。
2. 测试颜色空间、亮度归一化、遮边策略，保留原图以复核。
3. 返回 Top 3 候选及原始分数，不将模板分数称为经过概率校准的准确率。
4. 初始阈值 0.85、最近 5 帧中一致 3 帧为待验证起点，不是实测最优参数。
5. 未知、空槽、遮挡、Top 1/Top 2 差距很小的情况进入人工确认，不伪造高分。
6. 多帧稳定仅表示视觉候选稳定；仍不代表购入和拥有。

## 输出与接口边界

视觉对象可包含 `kind / id / region / frame_time / confidence / raw_score / source / ownership / confirmed`。`ownership=shop` 的候选与已有资源分开保存。

用户核对并确认购入后，前端转换成 API V1 的 `champion_ids / item_ids / top_k`；英雄去重，装备数量保留。初版稳定后只在用户确认或输入变更时请求推荐。尚未实现的 `/api/v1/vision/confirm` 不作为现阶段依赖。

采集进程与 FastAPI 之间的启动、停止、轮询或事件流协议尚待第二周与 A 约定，本周不新增服务端接口或改动 A 的算法。

## 后续验证门槛

- 采集：实机连续运行 5 分钟，检查最小化、遮挡、尺寸变化和恢复。
- 图像：使用独立标注测试集，分别统计英雄、装备 Top-1、未知拒识、修正率与平均耗时。
- 识别目标 85% 来源于计划，只能在样本数量、条件、划分和实验结果记录齐全后报告。
- 首次冻结模板后再划分测试截图，避免同图裁剪后同时进入模板和测试集。
